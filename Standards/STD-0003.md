# Engineering Document Lifecycle Standard

> [!abstract]
> Настоящий стандарт определяет единый жизненный цикл инженерных документов Knowledge Base организации Sun Decor.
>
> Стандарт устанавливает допустимые состояния документа, правила перехода между ними и требования к сопровождению документации на протяжении всего её существования.
>
> Цель стандарта — обеспечить предсказуемость, прослеживаемость и единообразное управление инженерной документацией.

---

# Purpose

Стандарт существует для определения единого жизненного цикла инженерных документов.

Он позволяет:

- унифицировать сопровождение документации;
- обеспечить понятный статус каждого документа;
- исключить неоднозначность использования документов;
- повысить качество инженерной документации;
- упростить сопровождение Knowledge Base.

---

# Scope

Настоящий стандарт распространяется на всю инженерную документацию Knowledge Base.

В частности:

- Architecture Decision Records (ADR);
- Engineering Documents (ENG);
- GitHub Domain Model (GITHUB);
- Engineering Standards (STD);
- Engineering Processes (PROC);
- Engineering Templates (TPL);
- иные инженерные документы организации.

---

# Lifecycle

Каждый инженерный документ проходит следующие стадии жизненного цикла.

```text
        Draft
          ▲
          │
          ▼
       Review
          │
          ▼
      Approved
          │
          ▼
     Deprecated
          │
          ▼
       Archived
```

Переход между состояниями осуществляется последовательно.

Возврат документа из состояния **Review** в **Draft** допускается по результатам инженерной проверки.

Иные обратные переходы допускаются только при создании новой редакции документа либо при наличии отдельного архитектурного решения.

---

# Lifecycle Mapping

Настоящий стандарт определяет **базовую модель жизненного цикла** инженерной документации.

Отдельные типы документов могут использовать специализированную терминологию, если она является отраслевым стандартом и не изменяет смысл жизненного цикла.

Например, **Architecture Decision Records (ADR)** используют классические статусы ADR.

| Generic Lifecycle | ADR Status |
|-------------------|------------|
| Draft | Proposed |
| Review | Under Review *(опционально)* |
| Approved | Accepted |
| Deprecated | Deprecated |
| Archived | Superseded / Archived |

Использование специализированной терминологии не изменяет логическую модель жизненного цикла инженерной платформы Sun Decor.

---

# Lifecycle States

## Draft

Документ находится в разработке.

Допускаются любые изменения структуры и содержания.

Документ не считается частью действующей инженерной документации.

---

## Review

Документ завершён автором и передан на инженерную проверку.

На данном этапе оцениваются:

- полнота;
- соответствие архитектуре;
- отсутствие противоречий;
- качество оформления;
- корректность ссылок;
- соблюдение действующих стандартов.

По результатам проверки документ либо принимается, либо возвращается в состояние **Draft** для доработки.

---

## Approved

Документ принят и считается действующим.

Он становится официальной частью инженерной платформы Sun Decor и может использоваться как нормативный источник.

Изменения допускаются только через установленный процесс сопровождения документации.

---

## Deprecated

Документ признан устаревшим.

Он сохраняется для обеспечения совместимости и исторической прослеживаемости, однако не рекомендуется для использования в новых инженерных решениях.

При наличии замещающего документа должна быть указана ссылка на него.

---

## Archived

Документ полностью выведен из активного использования.

Он сохраняется исключительно как исторический артефакт.

Архивный документ не развивается и не используется в текущей инженерной практике.

---

# State Transitions

Допустимые переходы между состояниями.

| From | To |
|-------|----|
| Draft | Review |
| Review | Draft |
| Review | Approved |
| Approved | Deprecated |
| Deprecated | Archived |

Иные переходы допускаются только при наличии отдельного архитектурного решения.

---

# Rules

> [!important]
> Требования данного раздела являются обязательными.

## Rule 1 — Single Status

Каждый инженерный документ обязан иметь ровно один актуальный статус.

---

## Rule 2 — Explicit Lifecycle

Статус документа должен быть явно указан в YAML Front Matter.

Для большинства инженерных документов используются статусы, определённые настоящим стандартом.

Для специализированных типов документов допускается использование эквивалентной терминологии, если это предусмотрено соответствующим отраслевым стандартом.

---

## Rule 3 — Traceability

Изменение статуса должно быть прослеживаемым.

При необходимости рекомендуется фиксировать причины изменения статуса в журнале изменений, соответствующем ADR или иной инженерной документации.

---

## Rule 4 — Deprecated Documents

Документ со статусом **Deprecated** должен содержать ссылку на актуальную замену, если такая существует.

---

## Rule 5 — Archived Documents

Архивные документы не изменяются.

Допускается исправление исключительно технических ошибок (например, битых ссылок или форматирования), не изменяющих смысл документа.

---

# Recommendations

Рекомендуется:

- минимизировать время нахождения документа в состоянии **Review**;
- не использовать документы со статусом **Draft** в качестве нормативных источников;
- своевременно переводить устаревшие документы в состояние **Deprecated**;
- архивировать документы только после завершения их жизненного цикла;
- сохранять историю изменений независимо от текущего статуса.

---

# Exceptions

Исключения допускаются только при наличии документированного архитектурного решения.

---

# Rationale

Инженерная документация является частью инженерной платформы и требует такого же управления жизненным циклом, как и программные продукты.

Единый жизненный цикл обеспечивает:

- предсказуемость;
- прозрачность;
- прослеживаемость;
- единые правила сопровождения;
- снижение количества устаревшей документации.

Разделение состояний позволяет явно определить степень зрелости каждого документа и исключает неоднозначность при его использовании.

Использование специализированной терминологии для отдельных типов документов (например, ADR) позволяет сохранять совместимость с общепринятыми инженерными практиками без нарушения единой модели жизненного цикла организации.

---

# Compliance

Стандарт считается соблюдённым, если:

- документ имеет один допустимый статус;
- статус указан в YAML Front Matter;
- переходы между состояниями соответствуют настоящему стандарту;
- устаревшие документы имеют корректный статус;
- архивные документы не изменяются;
- при наличии замещающего документа указана ссылка на него.
