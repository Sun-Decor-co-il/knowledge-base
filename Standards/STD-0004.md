# Engineering Metadata Standard

> [!abstract]
> Настоящий стандарт определяет единые требования к метаданным инженерных документов Knowledge Base организации Sun Decor.
>
> Стандарт устанавливает обязательные поля YAML Front Matter, правила их заполнения и использования.
>
> Цель стандарта — обеспечить единообразие, машиночитаемость и автоматизируемость инженерной документации.

---

# Purpose

Стандарт существует для унификации метаданных инженерных документов.

Он позволяет:

- обеспечить единообразное оформление документации;
- повысить качество навигации;
- упростить автоматическую обработку документов;
- обеспечить возможность проверки документации средствами автоматизации;
- сделать инженерную документацию предсказуемой.

---

# Scope

Настоящий стандарт распространяется на всю инженерную документацию Knowledge Base.

В частности:

- Architecture Decision Records (ADR);
- Engineering Documents (ENG);
- GitHub Domain Model (GITHUB);
- Engineering Standards (STD);
- Engineering Processes (PROC);
- Engineering Templates (TPL);
- иные инженерные документы организации.

---

# Metadata Structure

Каждый инженерный документ должен начинаться с YAML Front Matter.

Общий вид:

```yaml
---
id:
title:
status:
date:
tags:
---
```

Обязательные поля (`id`, `title`, `status`, `date`, `tags`) образуют **минимальную совместимую схему метаданных (Minimum Metadata Schema)** для любого инженерного документа Sun Decor.

Любые дополнительные поля являются расширением данной схемы и не должны изменять или переопределять смысл обязательных полей.

Дополнительные поля допускаются, если они необходимы для конкретного типа документа и не противоречат настоящему стандарту.

---

# Metadata Fields

## id

Уникальный идентификатор документа.

Правила формирования определяются [[Engineering Document Identification Standard]].

Пример:

```yaml
id: STD-0004
```

---

## title

Официальное название документа.

Поле `title` должно совпадать с основным заголовком документа (`H1`).

Пример:

```yaml
title: Engineering Metadata Standard
```

---

## status

Текущий статус документа.

Для большинства инженерных документов используются значения, определённые [[Engineering Document Lifecycle Standard]].

Специализированные типы документов (например, ADR) могут использовать эквивалентную отраслевую терминологию.

Пример:

```yaml
status: "#approved"
```

---

## date

Дата публикации либо последнего утверждения документа.

Используется формат ISO 8601 (`YYYY-MM-DD`).

Пример:

```yaml
date: 2026-07-30
```

---

## tags

Список тематических тегов документа.

Теги используются для:

- навигации;
- поиска;
- построения связей;
- автоматической классификации.

Пример:

```yaml
tags:
  - engineering
  - standard
  - metadata
```

---

# Rules

> [!important]
> Требования данного раздела являются обязательными.

## Rule 1 — Required Metadata

Каждый инженерный документ обязан содержать YAML Front Matter.

---

## Rule 2 — Minimum Metadata Schema

Каждый инженерный документ обязан содержать все поля минимальной схемы метаданных:

- `id`
- `title`
- `status`
- `date`
- `tags`

Удаление или переименование обязательных полей не допускается.

---

## Rule 3 — Unique Identifier

Поле `id` является обязательным и должно быть уникальным.

---

## Rule 4 — Title Consistency

Поле `title` должно совпадать с названием документа (`H1`).

---

## Rule 5 — Lifecycle Status

Поле `status` является обязательным.

Используемые значения должны соответствовать [[Engineering Document Lifecycle Standard]] либо специализированным правилам конкретного типа документа.

---

## Rule 6 — Publication Date

Поле `date` является обязательным.

Дата фиксирует публикацию либо утверждение документа.

---

## Rule 7 — Tags

Каждый документ обязан содержать хотя бы один тег.

Рекомендуется использовать от трёх до семи тегов.

---

## Rule 8 — Extensibility

Дополнительные поля допускаются.

Они не должны изменять смысл обязательных полей и должны сохранять совместимость с минимальной схемой метаданных.

---

# Recommendations

Рекомендуется:

- придерживаться единого порядка расположения полей;
- использовать короткие и понятные значения;
- избегать дублирующих тегов;
- использовать существующие теги вместо создания новых;
- не удалять метаданные после публикации документа;
- сохранять совместимость с минимальной схемой метаданных при добавлении новых полей.

---

# Recommended Field Order

Для обеспечения единообразия рекомендуется следующий порядок.

```yaml
---
id:
title:
status:
date:
tags:
---
```

# Exceptions

Дополнительные поля допускаются только при наличии объективной необходимости.

Удаление обязательных полей минимальной схемы не допускается.

---

# Rationale

Метаданные являются машинно-обрабатываемой частью инженерной документации.

Их стандартизация позволяет:

- автоматически анализировать документы;
- выполнять проверки качества;
- строить навигацию;
- генерировать индексы;
- использовать автоматизацию без привязки к содержимому документа.

Введение **Minimum Metadata Schema** обеспечивает единый контракт для всей инженерной документации. Благодаря этому любые инструменты автоматизации могут рассчитывать на наличие обязательного набора метаданных независимо от типа документа.

Дополнительные поля расширяют возможности конкретных типов документов, но не нарушают совместимость всей инженерной платформы.

---

# Compliance

Стандарт считается соблюдённым, если:

- документ содержит YAML Front Matter;
- присутствуют все поля минимальной схемы метаданных;
- значения обязательных полей соответствуют установленным правилам;
- порядок полей соответствует рекомендуемому;
- дополнительные поля не нарушают требования настоящего стандарта.
