## Context

Инженерная база знаний Sun Decor создаётся как единый источник знаний организации.

По мере развития проекта количество документов будет постоянно увеличиваться. Без единых правил оформления возникнут проблемы с навигацией, поиском, поддержкой актуальности информации и автоматизацией обработки данных.

Необходимо определить единый стандарт оформления документов Knowledge Base.

## Decision

Все документы Knowledge Base оформляются по единым правилам.

### 1. Один документ — одна тема

Каждый документ отвечает только на один конкретный вопрос.

Документ не должен объединять несколько независимых тем.

### 2. README.md является точкой входа

Корневой файл `README.md` является главным навигационным документом репозитория.

Он содержит:

- назначение репозитория;
- структуру разделов;
- быстрые ссылки;
- краткое описание каждого раздела.

README не используется для хранения инженерных знаний.

### 3. Использование YAML Properties

Каждый документ начинается с YAML-блока.

Минимальный набор свойств:

```yaml
---
id:
title:
status:
date:
tags:
---
```

Дополнительные свойства допускаются при необходимости.

### 4. Использование Wiki Links

Связи между документами оформляются исключительно посредством внутренних ссылок Obsidian.

Пример:

```text
[[ADR-0003]]
[[Engineering Workflow]]
[[GitHub Project]]
```

Использование дублирующей информации вместо ссылок не рекомендуется.

### 5. Использование тегов

Теги применяются исключительно для тематической классификации документов.

Основные категории тегов:

- область знаний;
- предметная область;
- жизненный цикл документа.

Теги не заменяют структуру каталогов.

### 6. Использование каталогов

Каталоги используются только для логического разделения крупных областей знаний.

Структура каталогов должна оставаться простой и стабильной.

Основные разделы:

- Vision
- ADR
- Engineering
- GitHub
- Processes
- Products
- Glossary
- Templates
- Archive

### 7. Именование документов

Название файла должно совпадать с названием документа.

Для ADR используется формат:

```text
ADR-0001.md
ADR-0002.md
```

Для остальных документов используется человекочитаемое название.

Например:

```text
Engineering Workflow.md

GitHub Project.md

Definition of Done.md
```

### 8. Использование Markdown

Все документы создаются в формате Markdown.

Не допускается использование проприетарных форматов хранения информации.

### 9. Источник истины

Каждая сущность описывается только в одном документе.

Другие документы должны ссылаться на него посредством Wiki Links.

Дублирование информации не допускается.

### 10. Поддержка актуальности

При изменении архитектурных решений связанные документы должны быть актуализированы.

Knowledge Base должна отражать текущее состояние организации.

## Consequences

Принятие данного стандарта обеспечивает:

- единый стиль оформления документов;
- предсказуемую структуру базы знаний;
- снижение количества дублирующей информации;
- улучшение навигации;
- удобство использования Obsidian Graph;
- возможность автоматизации с использованием Dataview и других плагинов Obsidian;
- масштабируемость базы знаний при росте количества документов.

Knowledge Base становится единым и актуальным источником инженерных знаний организации.
