# Issue Standard

> [!abstract]
> Настоящий стандарт определяет правила использования GitHub Issues в инженерной платформе Sun Decor.
>
> Стандарт устанавливает назначение Issues, требования к их созданию, содержанию и жизненному циклу в рамках инженерного процесса.
>
> Цель стандарта — обеспечить единообразное управление инженерной работой, прослеживаемость изменений и прозрачность процесса разработки.

---

# Purpose

Стандарт существует для определения единых правил использования GitHub Issues.

Он позволяет:

- формализовать инженерные инициативы;
- обеспечить единообразное описание работы;
- организовать управление разработкой;
- обеспечить прослеживаемость решений;
- создать основу для планирования и автоматизации.

---

# Scope

Настоящий стандарт распространяется на все GitHub Issues, создаваемые в репозиториях организации Sun Decor.

---

# Issue Lifecycle

Issue представляет собой управляемую единицу инженерной работы.

Типичный жизненный цикл выглядит следующим образом:

```text
Discussion
    │
    ▼
Issue Created
    │
    ▼
Project Planning
    │
    ▼
Implementation
    │
    ▼
Review
    │
    ▼
Closed
```

Статус выполнения Issue определяется соответствующим GitHub Project и его Workflow.

---

# Usage Principles

GitHub Issue используется для управления инженерной работой.

Issue должен:

- описывать одну инженерную задачу;
- иметь понятную цель;
- содержать достаточный контекст;
- быть пригодным для планирования;
- сопровождаться до завершения.

Issue не является местом архитектурных обсуждений или хранения документации.

---

# Issue Rules

> [!important]
> Требования данного раздела являются обязательными.

## Rule 1 — One Issue, One Responsibility

Каждый Issue должен описывать одну самостоятельную единицу работы.

Не допускается объединение нескольких независимых задач в одном Issue.

---

## Rule 2 — Clear Objective

Issue должен содержать чётко сформулированную цель.

Исполнитель должен понимать ожидаемый результат без необходимости интерпретации требований.

---

## Rule 3 — Sufficient Context

Issue должен содержать информацию, достаточную для выполнения работы.

При необходимости должны быть указаны ссылки на:

- Discussion;
- ADR;
- инженерные стандарты;
- документацию;
- связанные Issues.

---

## Rule 4 — Traceability

Каждый Issue должен обеспечивать прослеживаемость инженерного процесса.

При наличии исходного обсуждения рекомендуется указывать ссылку на соответствующую GitHub Discussion.

Если работа приводит к изменению архитектуры или инженерных правил, должны быть указаны соответствующие ADR или Standards.

---

## Rule 5 — Workflow Integration

Каждый Issue должен быть включён в соответствующий GitHub Project.

Управление статусом Issue осуществляется исключительно средствами утверждённого Engineering Workflow.

---

## Rule 6 — Single Source of Work

Issue является единственным источником информации о выполняемой инженерной работе.

Дублирование описания задачи в других системах управления не допускается.

---

# Recommendations

Рекомендуется:

- использовать понятные и краткие заголовки;
- описывать ожидаемый результат, а не способ реализации;
- прикладывать необходимые материалы;
- связывать Issue с Milestone при планировании релиза;
- связывать Issue с Pull Request после начала реализации.

---

# Exceptions

Допускается создание технических или административных Issues без предварительной Discussion, если изменение:

- не влияет на архитектуру;
- не изменяет инженерные процессы;
- не требует принятия инженерного решения.

---

# Rationale

GitHub Issue является основной единицей управления инженерной работой.

Использование единых правил позволяет:

- обеспечить прозрачность процесса разработки;
- упростить планирование;
- повысить прослеживаемость изменений;
- создать основу для автоматизации;
- отделить управление работой от обсуждения и документирования.

Issue связывает инженерные решения с их практической реализацией и обеспечивает непрерывность процесса от идеи до результата.

---

# Compliance

Стандарт считается соблюдённым, если:

- Issue описывает одну самостоятельную задачу;
- цель сформулирована однозначно;
- приведён необходимый контекст;
- Issue включён в GitHub Project;
- связи с другими инженерными артефактами документированы.
