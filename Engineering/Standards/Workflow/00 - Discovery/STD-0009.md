# Discussion Standard

> [!abstract]
> Настоящий стандарт определяет правила использования GitHub Discussions в инженерной платформе Sun Decor.
>
> Стандарт устанавливает назначение Discussions, случаи их применения и место в инженерном процессе.
>
> Цель стандарта — обеспечить прозрачное принятие инженерных решений до начала реализации.

---

# Purpose

Стандарт существует для определения единых правил использования GitHub Discussions.

Он позволяет:

- обеспечить совместное обсуждение инженерных вопросов;
- отделить исследование от реализации;
- документировать процесс принятия решений;
- сократить количество преждевременных задач;
- повысить качество инженерных решений.

---

# Scope

Настоящий стандарт распространяется на все GitHub Discussions организации Sun Decor.

---

# Discussion Lifecycle

Discussion является начальной точкой инженерного процесса.

Типичный жизненный цикл выглядит следующим образом:

```text
Idea
    │
    ▼
Discussion
    │
    ▼
Decision
    │
    ▼
Issue
```

Discussion может завершиться:

- созданием Issue;
- принятием ADR;
- обновлением документации;
- отклонением идеи;
- отсутствием дальнейших действий.

---

# Usage Principles

GitHub Discussion используется для вопросов, на которые ещё нет инженерного решения.

Discussion предназначена для:

- исследования;
- анализа;
- обмена мнениями;
- оценки альтернатив;
- подготовки решений.

Discussion не является инструментом управления разработкой.

---

# Discussion Rules

> [!important]
> Требования данного раздела являются обязательными.

## Rule 1 — Discussion Before Implementation

Любая значимая инженерная инициатива должна быть предварительно рассмотрена в Discussion либо иметь документированное обоснование отсутствия такого обсуждения.

Настоящее правило определяется архитектурным решением [[ADR-0016]].

---

## Rule 2 — One Topic

Каждая Discussion должна быть посвящена одной теме.

Не допускается обсуждение нескольких независимых вопросов в рамках одной Discussion.

---

## Rule 3 — Clear Outcome

Каждая Discussion должна завершаться понятным результатом.

Например:

- принято решение;
- принято решение не реализовывать идею;
- требуется дополнительное исследование;
- создан Issue;
- подготовлен ADR.

---

## Rule 4 — No Implementation Tracking

Discussion не используется для отслеживания выполнения работы.

После принятия решения управление разработкой осуществляется средствами GitHub Issues и GitHub Projects.

---

## Rule 5 — Preserve Context

Discussion не удаляется после завершения.

История обсуждений является частью инженерной памяти организации.

---

# Recommendations

Рекомендуется:

- формулировать проблему до обсуждения решения;
- описывать альтернативные варианты;
- фиксировать аргументы;
- ссылаться на связанные документы;
- завершать Discussion итоговым сообщением.

---

# Exceptions

Допускается создание Issue без предварительной Discussion для:

- очевидных исправлений;
- редакционных изменений;
- исправления опечаток;
- иных незначительных изменений, не влияющих на архитектуру или процессы.

---

# Rationale

GitHub Discussion отделяет процесс исследования от процесса реализации.

Такое разделение позволяет:

- принимать более качественные инженерные решения;
- уменьшить количество необоснованных задач;
- сохранить историю обсуждений;
- обеспечить прослеживаемость принятых решений;
- повысить прозрачность разработки.

Discussion является частью коллективной инженерной памяти организации и должна рассматриваться как источник контекста для последующих решений.

---

# Compliance

Стандарт считается соблюдённым, если:

- Discussion посвящена одной теме;
- обсуждение завершено явным результатом;
- реализация не ведётся непосредственно в Discussion;
- история обсуждения сохранена;
- значимые инициативы предварительно обсуждены либо имеют документированное исключение.
