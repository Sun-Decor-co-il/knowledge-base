# Release Standard

> [!abstract]
> Настоящий стандарт определяет правила использования GitHub Releases в инженерной платформе Sun Decor.
>
> Стандарт устанавливает назначение Releases, требования к их созданию и место в инженерном процессе.
>
> Цель стандарта — обеспечить единообразное управление поставкой инженерных результатов и прослеживаемость опубликованных изменений.

---

# Purpose

Стандарт существует для определения единых правил использования GitHub Releases.

Он позволяет:

- фиксировать опубликованные результаты разработки;
- обеспечить прослеживаемость поставок;
- связывать инженерную работу с выпущенными версиями;
- организовать единый процесс публикации изменений;
- создать основу для автоматизации релизов.

---

# Scope

Настоящий стандарт распространяется на все GitHub Releases организации Sun Decor.

---

# Release Concept

GitHub Release представляет собой опубликованный инженерный результат.

Release фиксирует состояние продукта в момент его поставки и служит официальной точкой отсчёта для конкретной версии.

Release завершает процесс поставки изменений, но не жизненный цикл продукта.

---

# Usage Principles

GitHub Release используется исключительно для публикации инженерных результатов.

Release:

- представляет опубликованную версию продукта;
- объединяет завершённые изменения;
- может ссылаться на один или несколько Milestones;
- не используется для управления разработкой;
- не заменяет систему документирования изменений.

---

# Release Rules

> [!important]
> Требования данного раздела являются обязательными.

## Rule 1 — Published Result

Каждый Release должен соответствовать фактически опубликованному состоянию продукта.

Создание Release без публикации результата не допускается.

---

## Rule 2 — Traceability

Release должен обеспечивать прослеживаемость инженерной работы.

При необходимости должны быть указаны ссылки на:

- Milestones;
- Pull Requests;
- Issues;
- документацию.

---

## Rule 3 — Version Identification

Каждый Release должен иметь уникальный идентификатор версии в соответствии с принятой схемой версионирования.

Конкретная схема версионирования определяется отдельным стандартом.

---

## Rule 4 — Release Notes

Каждый Release должен сопровождаться кратким описанием опубликованных изменений.

Release Notes должны отражать содержание поставки, а не процесс разработки.

---

## Rule 5 — Stable Publication

После публикации Release не изменяется.

Исправления поставляются посредством нового Release.

---

## Rule 6 — Workflow Completion

Публикация Release означает завершение соответствующего Engineering Workflow для включённых изменений.

---

# Recommendations

Рекомендуется:

- публиковать Releases регулярно;
- использовать единый формат описания;
- связывать Release с соответствующими Milestones;
- использовать автоматическое формирование Release Notes при возможности;
- документировать значимые изменения продукта.

---

# Exceptions

Исключения допускаются только при наличии документированного архитектурного решения.

---

# Rationale

GitHub Release является официальной точкой публикации инженерных результатов.

Использование единых правил позволяет:

- обеспечить прозрачность поставок;
- повысить прослеживаемость изменений;
- связать инженерную работу с опубликованными версиями;
- подготовить процесс публикации к автоматизации;
- создать единый механизм управления версиями продуктов.

Release завершает процесс поставки изменений и фиксирует опубликованное состояние продукта.

---

# Compliance

Стандарт считается соблюдённым, если:

- Release соответствует опубликованному состоянию продукта;
- версия идентифицирована;
- Release сопровождается описанием изменений;
- обеспечена прослеживаемость инженерных артефактов;
- публикация выполнена в соответствии с настоящим стандартом.
